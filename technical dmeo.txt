# 1) System architecture (high level)

* **Client (React/TS)**

  * Visual canvas: `react-force-graph-3d` or a custom React-Three-Fiber scene if you want bespoke visuals. The ready component gives node physics + interactions out of the box. ([GitHub][4])
  * Local UI state, drag/rotate, right-click menu, editor modal, filters, visual cluster controls.
  * Offload heavy work (embedding projection, ANN queries) to the backend or to WebWorkers.

* **Backend**

  * Embedding service: call OpenAI embeddings (or your own sentence-transformer server) to convert files into vectors and metadata. Store raw file (blob or S3) + text/extracted text + vector. ([OpenAI Platform][5])
  * Vector DB: options:

    * **pgvector** (Postgres extension) — easy to run alongside relational metadata. Good for prototyping/self-host. ([GitHub][6])
    * **Pinecone / Milvus / Weaviate** — managed or open-source vector DBs with high-performance ANN indexing for production scale. Pick based on your ops appetite. ([Pinecone Docs][7])
  * Indexing / reduction: store the original high-dim vectors; compute 3D projection (PCA → UMAP) for the visual positions and cache it. ([pair-code.github.io][8])
  * Realtime sync: WebSocket + Yjs awareness for collaborative cursor/selection + CRDT document sync. ([docs.yjs.dev][3])

* **Worker pipeline**

  * File ingestion → extract text (OCR for images) → chunk large documents (sliding window) → compute embedding per chunk → store chunk vectors + parent doc id → compute doc-level vector (e.g., mean or weighted aggregation).
  * Periodically recompute clusters / UMAP for whole dataset or per-project.

---

# 2) Vector / embedding design (practical)

* **Model choices**

  * Fast / cheap: `all-MiniLM-L6-v2` → 384-dim (great for interactive apps). ([Hugging Face][2])
  * Higher quality: MPNet / OpenAI `text-embedding-3-small/large` (larger dims, better semantic fidelity). Keep the original high-dim vector for retrieval and only project to 3D for visualization. ([OpenAI Platform][5])
* **Multi-modal (images + text)**

  * Use a visual embedding (CLIP / similar) and either concatenate or learn a projection to the same space (or keep two spaces and hybrid-score). For UX, keep one “visual position” space to place nodes.
* **Chunking**

  * Long files → slice into 512–2048 token chunks with overlap; embed each chunk and store chunk metadata so you can show snippet provenance in search results (the UX needs to show “this match came from paragraph X”). [Pinecone and other vector DB guides discuss chunking; it’s standard]. ([pinecone.io][9])

# 3) Layout + physics ideas (makes the “space” feel alive)

* **Base positions:** use the 3D projection (UMAP/PCA) to set initial node positions in 3D “thought space.” ([pair-code.github.io][8])
* **Force rules:**

  * **Similarity attraction:** Attractive force magnitude ∝ similarity (cosine) between vectors.
  * **Citation springs:** If A cites B or A contains B, model a spring: preferred distance = small radius → produce orbital motion. Use trig + time to implement gentle orbit if you want deterministic circular orbits for “citation children.”
  * **Repulsive force / collision avoidance:** prevent overlap; cap force magnitudes to maintain stable motion.
  * **Damping + lerp smoothing:** positions should `lerp(target, 0.02)` so motion is floaty, not jittery.
* **Performance:** use Barnes-Hut or approximate force sim (d3-force variants used by force-graph) to scale to thousands of nodes. `react-force-graph-3d` already uses d3/ngraph methods. ([vasturiano.github.io][1])

UX affordances:

* Node size = centrality / citation count / recency.
* Node glow / color = cluster/topic tag.
* Orbit speed = “virality” (count of inbound citations).
* Pin / freeze a node to remove it from physics (useful for manual curation).

# 4) Organizational-psychology & UX rules (how to avoid cognitive overload)

* **Progressive disclosure:** don’t show every single neighbor at zoom-out. Show aggregated “cluster planets” that expand on zoom/click.
* **Make system suggestions explainable:** when you auto-suggest a link between two docs, show the top 1–2 overlapping chunks and a one-line LLM summary explaining *why* they’re related (provenance).
* **Avoid algorithmic echo chambers:** give users controls to tune similarity thresholds and to toggle “serendipity” mode (show low-similarity but high novelty items).
* **Affordances for creativity:** quick-create (right-click → New doc), quote-connect (select node A → create child B pre-populated with quote snippet), snapshots/bookmarks of views, and “focus mode” (reduce distractions).
* **Cognitive limits:** cap default visible neighbors to ~6–10; allow “expand more” on user action.

---

# 5) Collaboration, versioning, and sync

* **Realtime editing:** use **Yjs** to sync document contents, node positions, and selection state. It’s battle-tested for Google-Docs/Figma style sync. ([docs.yjs.dev][3])
* **History / branching:** treat each document as a CRDT/text with version history and a “fork” action. Keep edit provenance and allow merge or create a link that indicates derivation.
* **Conflict handling:** CRDTs avoid manual merges for concurrent edits; for structural edits (node delete/move) show “replayer” UI to roll back.

---

# 6) Storage, search & scale (ops)

* **Store**: file blobs in S3, metadata in Postgres, vectors in pgvector (or use Pinecone/Milvus for scale). pgvector gives you the convenience of relational queries + vector search for prototypes. ([GitHub][6])
* **ANN index choices**: HNSW is a solid general choice; use Faiss or HNSWlib if you want in-memory speed + custom ops. For production serverless, Pinecone/Milvus/Weaviate provide managed indexes. ([Zilliz][10])
* **Projection caching:** compute 3D UMAP projection on the backend, cache results, and only recompute on significant dataset changes (or do incremental updates). UMAP is a good tradeoff for preserving both local & global structure and scales better than t-SNE. ([pair-code.github.io][8])

# 8) Small starter code (React + node sketch)

Below is a **tiny** starter to get the visual canvas going. This uses `react-force-graph-3d` for an interactive 3D force graph. (Install: `npm i react-force-graph three @types/three`)

```tsx
// App.tsx (React + TS)
import React, { useRef, useState, useEffect } from 'react';
import ForceGraph3D, { ForceGraphMethods } from 'react-force-graph-3d';

type Node = { id: string; title?: string; size?: number; vec?: number[]; pinned?: boolean };
type Link = { source: string; target: string };

export default function App() {
  const fgRef = useRef<ForceGraphMethods | null>(null);
  const [graph, setGraph] = useState({ nodes: [] as Node[], links: [] as Link[] });

  useEffect(() => {
    // seed demo
    setGraph({
      nodes: [
        { id: 'business_ideas', title: 'business_ideas', size: 12 },
        { id: 'ai_startup', title: 'AI startup', size: 6 },
        { id: 'visualizer', title: 'Visualizer idea', size: 6 }
      ],
      links: [
        { source: 'ai_startup', target: 'business_ideas' },
        { source: 'visualizer', target: 'business_ideas' }
      ]
    });
  }, []);

  return (
    <div style={{ width: '100vw', height: '100vh' }}>
      <ForceGraph3D
        ref={fgRef}
        graphData={graph}
        nodeLabel={(n: any) => `${n.title}`}
        nodeAutoColorBy="group"
        nodeThreeObject={(node: any) => {
          // simple sphere scaled by node.size
          const sprite = new THREE.Mesh(
            new THREE.SphereGeometry((node.size || 4) * 0.2, 16, 16),
            new THREE.MeshStandardMaterial({ metalness: 0.2, roughness: 0.7 })
          );
          return sprite;
        }}
        onNodeClick={(node) => {
          // open editor modal (pseudo)
          alert('Open editor for ' + (node as any).id);
        }}
        onNodeDragEnd={(node: any) => {
          // pin node when user moves it
          node.fx = node.x;
          node.fy = node.y;
          node.fz = node.z;
        }}
        cooldownTicks={100}
        enableNodeDrag={true}
      />
    </div>
  );
}
```

# 9) Key tradeoffs you should know

* **Client-only vs server embeddings:** Client-only (in-browser) is privacy-friendly but heavy on resources; server embeddings are easier and cheaper to run with good models and allow central indexing. ([Hugging Face][2])
* **Vector DB choices:** pgvector = easiest to prototype, Pinecone/Milvus = scale. ([GitHub][6])
* **Projection consistency:** UMAP is great for UX but non-deterministic between runs (seed it or cache). Use PCA + small UMAP steps for stability. ([pair-code.github.io][8])

## Example REST flow (create document + view on canvas)

1. Client `POST /projects/{p}/documents` → server creates doc row (status `pending`) and returns `docId`.
2. Server enqueues ingest job `ingest:{docId}`.
3. Worker extracts text, chunks, computes embeddings, writes chunk embeddings to `doc_chunks` and `embeddings`. Worker calculates doc vector (mean or weighted) and writes to `doc_embeddings`.
4. Worker triggers recompute/append to projection queue or writes new coordinates for the specific doc in `projection_updates` table. Alternatively, at scheduled intervals recompute UMAP for whole project.
5. Client polls or receives WebSocket event `document:updated` and then requests `GET /projects/{p}/projection` (or client receives `projection:updated`) and updates canvas.

# DB SCHEMA (Postgres + pgvector recommended)

Below is a practical schema (DDL snippets). Assume `pgvector` extension is installed.

### Extensions

```sql
-- enable extensions
CREATE EXTENSION IF NOT EXISTS "pg_trgm";
```

### 1) `users`

```sql
CREATE TABLE users (
  id uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  email text UNIQUE NOT NULL,
  name text,
  hashed_password text,
  created_at timestamptz DEFAULT now(),
  profile jsonb
);
```

### 2) `projects`

```sql
CREATE TABLE projects (
  id uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  owner_id uuid REFERENCES users(id) ON DELETE SET NULL,
  name text NOT NULL,
  description text,
  settings jsonb DEFAULT '{}'::jsonb,
  created_at timestamptz DEFAULT now(),
  updated_at timestamptz

CREATE INDEX idx_projects_owner ON projects(owner_id);
```

### 3) `project_members`

```sql
CREATE TABLE project_members (
  project_id uuid REFERENCES projects(id) ON DELETE CASCADE,
  user_id uuid REFERENCES users(id) ON DELETE CASCADE,
  role text CHECK (role IN ('owner','editor','viewer')),
  PRIMARY KEY (project_id, user_id)
);
```

### 4) `files`

```sql
CREATE TABLE files (
  id uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  project_id uuid REFERENCES projects(id) ON DELETE CASCADE,
```

## Indexing & search considerations

* **Vector ANN index**: `ivfflat` or `hnsw` on embedding columns (depending on pgvector / DB support). Tune `lists` or HNSW params depending on dataset size & QPS.
* **Text search**: maintain a `tsvector` column on documents and chunks and GIN index for full-text search. Example:

```sql
ALTER TABLE documents ADD COLUMN content_tsv tsvector;
CREATE INDEX idx_documents_text ON documents USING GIN(content_tsv);
-- use trigger to update tsvector on insert/update (or compute in ingestion pipeline)
```

* **Hybrid search**: combine full-text ranking (`ts_rank`) with ANN vector score; return both and expose combined ranking in API.

# Operational notes & best practices

* **Chunking policy:** default 512–1024 tokens with 20–30% overlap. Store chunk mapping so search can show exact snippet provenance.
* **Projection recompute cadence:** for large projects, schedule UMAP/PCA recompute during off-peak or use incremental update for new nodes. Cache the projection version and send clients the version to avoid mismatch.
* **Worker architecture:** use a background job queue (Redis / RabbitMQ / Sidekiq / Celery). Workers: file extraction, OCR, chunking, embedder, indexer, projection worker.
* **Embeddings model choice:** pick one model for the project corpus to keep vector dimension consistent; if changing models, plan re-embedding migration.
* **Permissions:** enforce project-level ACLs in every endpoint. Signed S3 URLs for uploads. Rate-limit embedding requests to provider.
